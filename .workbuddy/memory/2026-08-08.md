## 修复清晰度/降噪"前向声明类"编译红 (commit f2a3e8c)
- 用户贴真实报错：`DYYYPlaybackQualityNoise.xm:123` `receiver type 'AWEPlayerPlayControlHandler' for instance message is a forward declaration`；同文件 `property 'availableQualities' cannot be found in forward class`。
- **根因**：`AWEPlayerPlayControlHandler` 在本仓库 `AwemeHeaders.h` 仅为 `@class` 前向声明（私有抖音类，无完整 `@interface`）。`%hook` 内用 `[self switchToQuality:0]`(调 %new 方法) 与 `self.availableQualities`(访问 %property) 时，编译器只看到前向声明，找不到这些成员 → 报 forward declaration。对照：`DYYYLongPressPanel.xm` 的 `%property` 能过是因为那个类在本仓库是完整 @interface。

- **可复用铁律**：hook 任何私有抖音类（`AwemeHeaders.h` 里只有 `@class Xxx` 的）时，一律用「分类声明方法/属性 + 手写 associated object 存取器」替代 `%property`，否则必中 forward declaration 红。详见 MEMORY.md 同名条目。

## 修复"分类无法依附前向声明基类"编译红 (commit df16949) —— 最终解
- 用户再贴 CI 红：`DYYYPlaybackQualityNoise.xm:15` `cannot find interface declaration for 'AWEPlayerPlayControlHandler'; did you mean 'AWEDPlayerPlayControlContainer'?` + 后续一堆 `receiver type 'AWEPlayerPlayControlHandler' for instance message is a forward declaration` / `property 'xxx' cannot be found in forward class`。
- **根因（上一次 f2a3e8c 修法不彻底）**：分类 `@interface Xxx (DYYYQualityNoise)` **必须依附一个完整基类 `@interface Xxx`**；而本仓库 `AwemeHeaders.h` 里该类**只有 `@class` 前向声明、无完整 `@interface`**。直接写分类 → 编译器报 "cannot find interface declaration"。分类内 `@property` 也无法合成（accessor 方法不生成 → `self.xxx` 失败）。
- **最终修法**：
  1. 分类**之前**补完整基类声明 `@interface AWEPlayerPlayControlHandler : NSObject @end`（编译期虚构类型；运行期 Logos 按类名 hook 真实私有类，互不干扰）；
  2. 分类内 `@property` 全部改为**方法声明**（getter/setter 对），实际由下方 `%new` 手写 associated object 存取器实现；
  3. 验证：无 `@property` 残留；8 个 %new 方法 + 5 个属性存取器全部有声明与实现；本文件无裸 `@class` 冲突。
- **与 f2a3e8c 的区别**：f2a3e8c 只加了"分类"却缺"基类声明"，分类挂不上才二次红。正确顺序 = 基类 `@interface Xxx : NSObject` → 分类声明方法/存取器 → `%hook` + `%new` 实现。
- 已推送 `df16949`（f2a3e8c..df16949）。待用户查 Actions 是否绿。

## 修复 ObjC++ 编译红 typeof（CI 报错，commit c5b470a）
- CI 报 `DYYYPlaybackQualityNoise.xm:167/169` `expected unqualified-id`（`__weak typeof(self) wself = self;` / `__strong typeof(wself) sself = wself;`）。
- **根因**：`.xm` 经 theos 预处理为 `.xm.mm`，按 **Objective-C++** 编译。`typeof` 是 GNU 扩展，在 C++/ObjC++ 模式下**不是关键字** → 报错。必须用编译器内建 `__typeof__`（C/C++/ObjC/ObjC++ 全模式可用）。
- **修复**：`typeof(self)` → `__typeof__(self)`（两处），其余逻辑不变（单例永不释放，block 捕获 self 无循环引用风险）。
- 已推送 `c5b470a`（af513d7..c5b470a）。**铁律已入 MEMORY.md**：`.xm` 里一律用 `__typeof__` 而非 `typeof`。待用户查 Actions 是否绿、真机复验清晰度+降噪。

## 深挖 DYYYSocialStats.xm 源码级分析（用户点名要分析该功能）
- 实际性质：**名字叫"统计"，本质是数字伪造工具，不是真统计**。约 1080 行，含 `DYYYVideoEditViewController` 编辑弹窗、分类、6 个 %hook 块。
- 做了什么：
  - 账号维度：Hook `AWEUserModel` 的 `followerCount`/`diggCount`/`followingCount`/`friendCount`/`mutualFriendCount` 等 getter，返回用户自定义值（键 `DYYYCustomFollowers`/`DYYYCustomLikes`/`DYYYCustomFollowing`/`DYYYCustomMutual`，开关 `DYYYEnableSocialStatsCustom`）；同时 Hook `AWEProfileSocialStatisticView` 的 `setFansCount:`/`setPraiseCount:` 直接传伪造值。
  - 视频维度：Hook `AWEAwemeModel`/`AWEAwemeStatisticsModel` 的 digg/comment/collect/share/forward count getter + `AWEFeedVideoButton setCount:`，返回自定义值（键 `DYYYVideoCustomLikes` 等，开关 `DYYYEnableVideoStatsCustom`）。
  - **高危写法**：Hook `NSDictionary objectForKey:`（Foundation 最底层、全 App 及系统库最频繁调用的方法），把 `@"fans_count"` 等键的返回值替换为伪造数字。白名单判断也难完全免疫，崩其他功能风险高。
- 影响范围：仅本地 UI 呈现被篡改，不影响服务器真实数据（自欺式显示修改）。
- 本地现状：`DYYY.xm` 仅 grep 到 `statisticsVideoViewedWithID:`（真实观看行为埋点上报）与 `@"statistics.diggCount"` 字典键，**无任何 `DYYY*SocialStatsCustom` / `DYYY*CustomFollowers` 伪造键** → 本地完全没有该伪造功能（也不需要）。
- 结论/建议：**不建议搬**。理由：①取向是造假（虚荣数据），非隐私/体验增强；②全局 `NSDictionary objectForKey:` Hook 高危，可能带崩其他功能；③若用户真想要"查看自己真实数据分布"，此文件给不了（它只能填假数字），需另做真实统计。之前第二轮初评"不推荐搬"判断成立。
